# WDR 模块开发规范

状态：已用于本次获准的 P0/P1 七模块本地改造，P2 后续按需执行；软件证据及未部署范围见[实施记录](validation/module_api_p0_p1_20261115.md)。基线日期：2026-11-15。适用范围：ModuleIndex 登记的 WDR-Xrobot-org 模块。本文参照已加载的 xrobot、xrobot-contrib 技能及官方索引全部 30 个模块的主头文件，不修改技能。

配套材料：[逐模块改造方案与源码基线](module_api_migration_plan.md)、[模块文档约定](module_documentation.md)。工具基线为本机与工程一致的 XRobot 1.0.1、libxr 6.0.1、LibXR v2.0.1（5161373d）。

## 1. 官方共有约定与 WDR 选择

| 项目 | 官方源码体现的约定 | 本提案的 WDR 规则 |
| --- | --- | --- |
| 构造接口 | 对象依赖优先，配置随后；简单标量、聚合 Param、initializer_list 均有实例 | 沿用这三种形式，不强制所有模块使用 Param |
| 复杂配置 | BMI088、CanIMU、MadgwickAHRS 等使用尾部 Param，构造默认实参写出字段与取值 | 同类模块保持一致；Topic、命令名、任务配置和算法调参集中到 Param |
| 简单配置 | BlinkLED、BuzzerAlarm、R9DS、STP23L 等使用独立默认参数 | 参数少且语义独立时保留，不为包装而增加结构体 |
| Topic | 通过普通构造参数或 Param 字符串字段提供，manifest 无 Topic 键 | 输入输出须明确名称、类型、单位、坐标系、时序及有效性 |
| 依赖 | 必需对象通常为引用，可选对象可为指针 | 必需引用在最前；可选指针随后、配置之前，空值含义必须明确 |
| 生命周期 | 静态实例，构造与 OnMonitor 驱动；库模块可 standalone: false | 自主线程、同步组件、纯库分别说明，不强制给所有模块加线程、命令或 Topic |
| 默认值 | 各模块默认值与字段数量不同 | 保留算法与设备差异，不为统一外观统一噪声、增益、周期或栈大小 |

依据是[官方模块索引](https://github.com/xrobot-org/xrobot-modules/blob/master/index.yaml)与各模块源码，逐项取样记录见配套方案附录。官方并没有“所有模块只能用一种 Param 形式”的统一事实。本规范新增的集中配置、兼容策略和检查要求属于 WDR 的拟定选择。

## 2. 构造与配置接口

### 2.1 依赖和参数顺序

1. 必需外设、数据库、RamFS、其他模块对象放在最前，使用引用，不设默认值。
2. 可选对象使用指针。若后面仍有无默认值的配置，则可选指针也不设默认实参，YAML 显式传 nullptr；不可给引用依赖补默认值来绕过顺序约束。
3. 配置放在依赖之后。复杂配置优先采用一个末尾 `const Param& param`；简单配置保留少量具名标量。
4. 同一个配置项只保留一个入口，不同时放在 Param 和独立参数中。
5. Topic、命令、数据库键属于实例配置，不属于硬件对象依赖。同类模块统一摆放位置。
6. 不提供无消费者的兼容构造、工厂层、配置继承层；是否迁移旧接口须在实施方案中单独决定。

下面是目标接口示意，不是本次已经实现或编译验证的接口：

```cpp
class AttitudeExample
{
 public:
  struct Param
  {
    const char* gyro_topic_name;
    const char* accel_topic_name;
    const char* output_topic_name;
    const char* diagnostics_topic_name;
    const char* command_name;
    uint32_t task_stack_depth;
  };

  AttitudeExample(LibXR::RamFS& ramfs,
                  const Param& param = {
                      .gyro_topic_name = "bmi088_gyro",
                      .accel_topic_name = "bmi088_accl",
                      .output_topic_name = "example_attitude",
                      .diagnostics_topic_name = "example_diagnostics",
                      .command_name = "example",
                      .task_stack_depth = 4096});
};
```

此形式参考 MadgwickAHRS、BMI088 等官方模块。示例只展示接口组织，不代表对算法必需参数、输入时序或输出布局的裁剪。

### 2.2 默认值的含义

- 区分字段默认成员初始化、构造函数默认实参和机器人 YAML 覆盖值，三者不能混称“默认值”。
- 面向 XRobot 的复杂配置优先使用可解析的具名聚合默认实参；避免依赖生成器无法展开的工厂表达式来隐藏配置。
- 类内默认实参不直接使用本类带默认成员初始化器的 `Param{}` 或 `{}`，遵守工程 AGENTS.md 中的 GCC 限制。确需另一种构造形式时先通过实际生成器和编译器验证。
- Param 是外部类型别名时，不机械套用本类嵌套类型的限制；先核对解析与编译结果。
- 迁移前后记录每个字段的有效值；字段迁入 Param 不得顺便更改数值、单位、枚举、坐标系或更新频率。
- 电机 ID、方向、几何、标定、机构 PID 等机器人参数由机器人 YAML 显式给出。默认值只用于模板或通用行为，不视为实机标定完成。
- EKF、ESKF、Madgwick 无需暴露相同数量的算法参数。新增算法调参入口应说明实际用户和影响；不把所有内部常量都提升成 YAML 参数。

### 2.3 XRobot 1.0.1 的 YAML 约束

本机 `constructor_model.py` 的 `_require()` / `_mapping()` 要求聚合映射的键与字段一致且按声明顺序排列；`config_edit.py` 的 `seed_value()` 会生成完整映射。这是本版本工具行为，不以 C++ 的部分聚合初始化能力推断 YAML 能力。

- args 按所选构造函数顺序填写；Param 映射列全字段，嵌套映射同样核对。
- Topic 和命令名保留双引号字符串语义，资源对象写注册名；指针表达式按已验证规则填写。
- “默认字段很多”不等于“进行了很多非默认调参”；评审须对比有效值，而非只数 YAML 行数。
- 不通过偷偷修改生成器、删减算法能力或手工编辑生成头来缩短配置。
- 原始 C++ 表达式、全默认聚合和部分指定初始化能否接受，须逐种由当前版本验证；不能把 `'{}'` 作为通用省略方案。
- 若将来确需仅写覆盖项，应另立 XRobot 工具改进方案，不能作为模块规范化的隐含前提。

## 3. Topic、状态与多实例

- README 的 Topic 表至少列方向、默认名称、C++ 类型、单位、坐标系、发布触发、时间戳来源及失效条件。
- 相同语义优先沿用当前字段名；`accel` / `accl` 等命名差异不可单独触发全组织破坏性重命名。需要统一时列出全部发布者与订阅者，作为独立迁移项。
- 同一时间戳配对与“最新加速度配陀螺”是不同输入契约，不能为了接口一致而互换。
- 连续目标快照和一次性事件分开定义；不得用覆盖式最新值存储代替必须逐次消费的事件。
- 模块管理自己的命令与状态，板级命令只负责板级观察。已有多实例模块的命令名、Topic 名、持久化键必须保持可配置且互不冲突。
- 不因规范化增加数据库键或改动消息结构、时间戳、枚举值、打包布局；通信布局变化单独评审。

## 4. 执行、资源与控制副作用

- 构造文档明确：是否阻塞、是否创建线程、是否注册回调、是否发 CAN/UART、是否使能电机、是否写 Flash。
- 自主模块在自己的线程推进；同步组件由所属任务驱动。保留 Launcher 与 Gimbal 同拍执行、PowerControl 由 Chassis 调用等既有关系。
- `OnMonitor()` 返回 void、能返回，不承担控制主循环；不为统一形式给纯库新增任务。
- 线程栈注明单位和原值；优先级、周期、队列容量只在有需求时暴露，不随 API 搬迁调整。
- 回调按现有上下文处理；ISR 不等待、不循环重试、不承担需阻塞的协议或控制流程。队列满时明确丢弃策略及计数。
- 缓冲、Topic 消息视图、对象引用与返回状态引用说明生命周期；状态读取是否为一致快照单独说明，不凭 `const` 推断线程安全。
- 复位覆盖哪些状态、失联后输出许可、恢复是否自动继续，均按现有行为记录。重命名 Reset 不得暗改恢复行为。
- 不附加没有明确需求的数值兜底、NaN/Inf 检查、重试或 fallback。

## 5. 模块仓库与文档

- 一个仓库维护一种模块/算法及其必要实现，不为统一接口另拆没有真实消费者的公共骨架库。
- manifest 使用 V2；依赖显式声明；纯库采用 standalone: false，不为需要静态实例装配的同步组件误标纯库。
- manifest 描述使用官方中英同行形式；自研注释采用中文，保留第三方原有注释和名称。
- CMake 集成 xr target，沿用当前工程与官方骨架方式；库或 Linux 模块的特殊构建依赖须明确，不机械复制 STM32 模板。
- README 参照 MadgwickAHRS，按模块作用、运行约定、构造接口、Topic、配置示例、依赖与硬件、来源与许可七节组织，使用编号和双语标题；详细来源与许可放第三方说明，迁移差异放 docs/migration.md。
- README 必须直接提供使用教学：`xrobot module add` → `xrobot setup` → `xrobot instance add` → 完整 YAML 参数示例与参数表 → `xrobot gen` → 可观察结果。命令使用真实模块 ID，依赖资源与实例顺序明确；不得用 example/examples 文件夹替代 README 中的教学。纯库模块改为 include 与最小调用教学，不创建 YAML 实例。具体写法见[模块文档约定](module_documentation.md)。
- 注释与格式遵循 AGENTS.md：lower_case、lower_case_、CamelCase、UPPER_CASE 与既有 clang-format；不批量重命名上游 API。
- 模块代码在模块仓库维护；框架只保存配置、锁定版本、集成及规范，下载目录不是框架源码交付物。

## 6. 改造与验收流程

1. 记录模块提交、构造签名、默认值与当前机器人有效值，列出真正的调用者、配置与依赖者。
2. 只做接口归位与文档变更；涉及有效值、更新步长、输入配对、输出布局、发送、门控的项另立行为修复。
3. 对比返回、容量、可见性与顺序、部分消费、阻塞与超时、完成与回调、所有权、复位恢复、执行上下文、兼容性与布局、资源与硬件副作用。无变化也须明确记录。
4. 在模块仓库完成解析、示例生成、必要的主机验证，再迁移真实 BSP 配置与直接 C++ 调用；生成头由工具更新。
5. 受影响 BSP 运行 Debug/Release 构建。硬件收发和机构闭环另验，不能用构建替代。
6. 上游 dev / 发布分支与 BSP 锁文件一起考虑；不得手改 lock 假装已消费某个修复。push、PR、合并、发布均不属于本次文档交付。
